# Infra Control Panel — Capability Audit (reuse vs build)

Date: 2026-06-05. Source: 6-agent parallel audit of the Press fork + frappe_theme_switcher (Watch Tower) codebase.
Goal: before building a live monitoring + control panel (server -> bench -> site/service, view logs, restart), map what already exists to reuse.

## Headline

> ~75% reuse: Press already has the service-status, per-service log, and restart primitives — the board is mostly an aggregator + a Vue page + two thin wrappers (per-service restart, Watch-Tower JSON), not a rebuild.

**Reuse estimate:** ~75% reuse / ~25% new build. Reuse: all data sources (supervisor status, logs, restart, ping, Prometheus usage, server/bench/site enumeration) and all UI building blocks (DevOverview layout, ObjectList badge-theme table, LogViewer drawer, confirmDialog, run_doc_method bridge). New build: one batched server→bench→service aggregator endpoint, one whitelisted per-service supervisorctl restart wrapper, a Watch-Tower→JSON status adapter for host-level disk/redis/mariadb/docker/microservice/agent probes, dashboard wrappers for the 6-7 ungated deploy_flow/ping methods, the server→bench→service tree page + service-row component, and auto-poll/caching.

## Gaps (must build)

### [SMALL] Whitelisted per-service restart endpoint. Bench.supervisorctl(action, programs) (press/press/doctype/bench/bench.py) can restart a single supervisor program but is not whitelisted. Need a @frappe.whitelist+@protected('Bench') wrapper that validates action in {start,restart} and the program name against get_processes output before calling supervisorctl(programs=[name]).

This is the literal 'click the service to restart it' requirement. Without it the panel can only restart the whole bench, not just redis or one worker.

### [LARGE] Single batched server->bench->service aggregator endpoint (@dashboard_whitelist get_infra_tree). Must fan out get_dev_overview_benches + per-bench get_processes + per-server check_memory_pressure/get_storage_usage/ping_* + the Watch-Tower JSON adapter, in parallel, normalize to one payload, and cache to a short Redis TTL.

No aggregate exists today; the UI would otherwise make N synchronous in-container supervisorctl-status execs (slow at scale) plus 4-5 scattered health calls per server on every refresh.

### [MEDIUM] Watch-Tower-checks -> JSON status adapter. Re-expose check_docker_container_health (drop unhealthy-only filter), check_ssh_connectivity, check_microservice_health (externalize the hardcoded service list), and optionally check_server_disk_usage reclaimable detail as read-only JSON that RETURNS the internal dicts, fans LOCAL-only probes out per server via ssh_cmd, and never emails or touches should_send_alert.

Watch Tower has the best SSH probes + thresholds for docker/ssh/microservice/disk-reclaimable, but every check_* returns only a bool and emails as a side effect — unusable by a live board as-is. check_mariadb_health's connection-pool SQL is also truncated/buggy and must be rewritten or skipped.

### [MEDIUM] Dashboard wrappers + role gates for the ungated MCP/ping methods: agent_health, agent_job_progress, agent_job_traceback, bench_provision_progress, site_status, deploy_candidate_status, lock.status (all @frappe.whitelist, no dashboard wrapper, no team-access gate — built for MCP token auth) and ping_agent/ping_mariadb/ping_agent_job/ping_ansible (@frappe.whitelist desk-only). Add press.api.server.check_agent_health mirroring the existing check_memory_pressure pattern, and @dashboard_whitelist (or System-Manager) wrappers for the rest.

Calling deploy_flow.* directly from the Vue dashboard runs them as the session user WITHOUT a team-access check; the ping_* are not in the dashboard allowlist at all. They power agent health, job-progress log streaming, and service dots, so they must be safely exposed.

### [MEDIUM] Server->bench->service tree page in the Vue dashboard (clone of DevOverview.vue) + a per-service-row component (generalize BenchWatchStatus.vue health-pill, or a 'service' ObjectList config object) + a right-side drawer shell (frappe-ui Dialog is centered-only).

DevOverview is bench-centric and has no server tier, no per-service rows, and no side drawer. The table/badge/expand mechanics are reusable but the server>bench>service grouping/aggregation UI layer is new.

### [SMALL] Live auto-refresh / caching layer. DevOverview shows a 'Live' badge but only refreshes on manual click. Add createResource .reload() on a 5-15s interval (or wire socket.js realtime), and back the aggregator with a short Redis TTL so polling does not re-run a synchronous supervisorctl-status exec per bench every tick.

The operator asked for a LIVE panel; without caching, frequent polling of N benches' container execs is too slow and load-heavy.

### [MEDIUM] Server / host-level system logs (journalctl, /var/log, systemctl status, docker daemon, standalone /var/log/mysql/error.log on dedicated DB servers) have NO whitelisted accessor — only Server.ansible_run (internal SSH, no whitelist) exists. A new role-gated wrapper with a FIXED command allowlist is needed if the drawer must show host/daemon logs beyond bench files.

log_browser.get_log only covers bench/site files written into the bench logs/ dir. A custom microservice or a daemon-level error log (nginx/redis/mysql on a dedicated server) has no path today.

### [SMALL] Microservices catalog. Press has NO doctype model for non-supervisor sidecar services (LiteLLM, Sanad Brain, MinIO, Code Analysis). check_microservice_health hardcodes a single service. A small config doctype (or settings list) of {name,url,server} is needed to drive the microservices row.

The board must list arbitrary microservices per server; there is no data source to enumerate them today.

## Proposed architecture

## Recommended architecture — maximize reuse, minimize new build

### 1. Page placement
Add a new System-Manager-gated route `/infra-board` in `dashboard/src/pages/` by **cloning `DevOverview.vue`** (it is already the target board: summary cards + filter bar + expandable per-row table + working restart actions via `run_doc_method`). Add a **server tier above benches** and **per-service rows below**. Reuse its `confirmDialog` restart plumbing and `buildBadgeClass()`/`ObjectListCell` Badge-theme mechanism unchanged. Generalize `BenchWatchStatus.vue` into a per-service health pill, or define a `'service'` config object for `ObjectList.vue` to get rows+badges+restart for near-free.

### 2. Data feed — ONE new aggregator, everything else reused
Build a single `@dashboard_whitelist get_infra_tree()` (the central new piece) that fans out, in parallel, and normalizes into a `server -> benches[] -> services[]` payload:
- **Servers**: `press.api.server.all` (add a System-Manager variant that ignores the team filter).
- **Benches**: `bench_dev_overview.get_dev_overview_benches` (as-is) grouped by its `server` field.
- **Per-bench services**: `press.api.bench.get_processes` -> `Bench.supervisorctl_status` -> `parse_supervisor_status` (the 8 supervisor programs incl. redis-cache/redis-queue/socketio/sshd). Pre-group with `group_supervisor_processes` / `sort_supervisor_processes`.
- **Per-server host services**: `press.api.server.check_memory_pressure` (host_memory_pressure, 60s cached) for memory; `Server.get_storage_usage` (@dashboard_whitelist) + `press.api.server.usage`/`analytics` for disk/cpu/load; `ping_mariadb`/`ping_agent`/`ping_agent_job`/`ping_ansible` for mariadb/agent/ssh dots; `deploy_flow.agent_health` (via a new `check_agent_health` wrapper) for the agent verdict.
- **Docker / ssh / microservice rows**: the new **Watch-Tower->JSON adapter** that reuses `_helpers.ssh_cmd` + `get_all_servers` + the exact SCAN_CMD / `docker ps -a` / curl-`/health` logic from `check_docker_container_health` / `check_ssh_connectivity` / `check_microservice_health`, but RETURNS dicts (no `send_alert_email`, no `should_send_alert`, no unhealthy-only filter, LOCAL probes fanned out per server). Skip `check_mariadb_health`'s truncated connection-pool SQL.

### 3. On-demand vs polled
- `supervisorctl_status` / `get_processes` are **synchronous in-container execs** (slow at scale) and `ssh_cmd` probes have up-to-30s timeouts. So: the aggregator caches results to a **short Redis TTL (~10-20s)**; the Vue page polls `get_infra_tree()` via `createResource.reload()` on a **5-15s interval** (DevOverview's manual-refresh becomes auto). `host_memory_pressure` already self-caches 60s. For an in-flight restart/deploy, **poll `agent_job_progress` every 3-10s** (it reads Agent Job rows, cheap) until the job leaves Running — this drives the live log/progress stream. No websocket needed for v1 (socket.js exists if a true push board is wanted later).

### 4. Logs drawer
Reuse the existing trio `LogBrowser/LogList/LogViewer.vue` and its backend `press.api.bench.logs` (file list) + `press.api.log_browser.get_log(log_type, doc_name, log_name)` (parsed, per-type FORMATTER_MAP covers bench/worker/frappe/database/scheduler/redis-cache/redis-queue/web.error). **Map each supervisor service row to its log file** (redis-cache->redis-cache.log, worker->worker.log, scheduler->scheduler.log) and call `get_log` on click; render with `LogViewer.vue` (level badges + search + pagination) inside a right-side drawer shell (small custom add since frappe-ui Dialog is centered-only). For a failed restart/deploy use `agent_job_traceback`. Host/daemon logs (journalctl, /var/log/mysql) are a gap — only `Server.ansible_run` exists, ungated; build a fixed-command-allowlist wrapper if needed.

### 5. Restart actions -> existing endpoints
- **Restart bench** -> `restart_bench_for_site` -> `Bench.restart_bench()` (already dashboard-callable, System-Manager-gated, audited; wired in `DevOverview.restartBench` with confirmDialog). Use `Bench.restart(web_only=True)` for near-zero-downtime web-only.
- **Restart one service** -> NEW ~3-line `@frappe.whitelist+@protected('Bench')` wrapper around `Bench.supervisorctl(action, programs=[name])`, restricting action to {start,restart} and validating the program name against `get_processes`.
- **Reboot server (VM)** -> `press.api.server.reboot` (as-is, HIGH risk, confirm + System-Manager + audit).
- **Restart MariaDB** -> `database_server.restart_mariadb` (HIGH risk, Ansible, confirm + maintenance window).
- **Restart agent** -> `Server.update_agent` (the only proxy; gate on `agent_health` verdict).
All wired through `press.api.client.run_doc_method`. **Safety gate**: call `agent_health`/`agent_job_progress` and **disable restart buttons when verdict in {slow,stuck}** — Press already uses this as `_GATE_A_GUARDED_TOOLS` to prevent corrupting a mid-migrate worker. Use `press.api.lock.status` to grey-out actions on a locked Site/Release Group.

### 6. Permission / security model (admin-only infra controls)
- **Page + aggregator**: `frappe.only_for('System Manager')` (match `get_dev_overview_benches`) — these are global ops controls, not team-scoped.
- **Convention**: call the `@protected` `api/*.py` wrappers (team/permission enforced) and expose new methods via `@dashboard_whitelist` or an explicit System-Manager check — never expose raw `Bench.docker_execute`, `Server.ansible_run`, or `ssh_cmd` to the client.
- **ssh_cmd contract**: commands MUST be hardcoded literals — the per-service restart and any host-log wrapper must whitelist a FIXED command/program set and validate identifiers against known data (get_processes program names, get_all_servers ips), never pass free-form user input.
