## Summary
Solid feature overall — security is handled correctly via `_safe()`, but there are two correctness bugs, one serious performance problem, and a D3 memory leak that will accumulate on repeated graph renders.

## Issues

- **[severity: high]** Performance — `health_graph.py` `extract_ast_graph`, lines 114–172: Every file in the app triggers 3 separate `docker_execute` calls (grep for class/def, grep for imports, grep for calls). For an app with 100 Python files that is 300 Docker round-trips, which is extremely slow. Fix: batch all three greps into a single shell pipeline per file, or — better — emit all three patterns in one `grep -E` pass and split the output by pattern in Python. Alternatively, run one `grep -rn` across the entire app directory and parse results server-side.

- **[severity: high]** Correctness — `health-d3.js` `renderCodeGraph`, line 293: `destroy()` calls `svg.on('click', null)` but does NOT call `sim.stop()` on any force simulation. The `render()` function creates a new simulation every call without storing a reference on `state`. When the Vue component unmounts or the user switches apps, the old simulation keeps ticking and firing `tick` events against detached DOM nodes, leaking CPU and references. Fix: store `sim` in `state` after creation (`state.sim = sim`), and in `destroy()` call `if (state.sim) state.sim.stop()`. Also stop `state.sim` at the top of `render()` before creating a new one.

- **[severity: medium]** Correctness — `health_graph.py` `extract_ast_graph`, lines 174–183: The deduplication loop only deduplicates edges between the same `(source, target)` pair. However, earlier in the same function (lines 144–148), module-level import edges are appended unconditionally for every file, so the same `(mod → target_mod)` pair can appear many times before deduplication. Those duplicates are correctly folded by the dedup block, which is fine. The real bug is on line 147: `if target_mod in modules` — this guard uses the `modules` dict which is built incrementally as files are processed. If the target module's first file is encountered *after* the current file, the import edge is silently dropped. Fix: run the import edge extraction in a second pass after all files are processed, so `modules` is fully populated.

- **[severity: medium]** Correctness — `health-d3.js` `renderCodeGraph` `getVisibleData`, lines 169–173: When the simulation mutates `data.edges` by resolving `source`/`target` to node objects (standard D3 forceLink behavior), the edge filter on the next call to `getVisibleData` checks both `e.source` (string) and `e.source?.id` (resolved object). This dual-form check works but is fragile. After the first `render()` call, `graphData.edges` has been mutated in-place by D3 — the string IDs are gone. A second `render()` call (e.g., drill-down then back) will filter using `.id` only, which is fine, but if `graphData` is ever reused across apps (it is — it comes from `graphCache`) the mutated edges break the module-level filter for all future renders. Fix: deep-clone `data.edges` before passing to `d3.forceLink`, or use `d3.forceLink(data.edges.map(e => ({...e})))`.

- **[severity: medium]** Vue lifecycle — `HealthAdvanced.vue`, line 127: `renderGraph()` calls `this._graphInstance.destroy()` before creating the new instance, which is correct. However, if `loadGraph()` is called again while `graphLoading` is already set (rapid app button clicks), the `await call(...)` in a previous invocation can resolve after `graphSelectedApp` has changed, causing `renderGraph(appName)` to be called for a stale app after `this._graphInstance` has already been replaced by a newer call. Fix: add a guard in the `finally` block or at the start of `renderGraph` to check that `appName === this.graphSelectedApp` before rendering.

- **[severity: low]** Correctness — `health_graph.py` `extract_codegraph`, line 67: Module grouping uses `parts[0]` of the file path. For codegraph output, `file` is the path relative to the app root (e.g., `myapp/module/file.py`), so `parts[0]` is the app name, not the module. All symbols would be grouped under one module (the app name). The AST fallback at line 118 strips the `apps/{app}/` prefix first and uses `parts[0]` correctly. The codegraph path needs the same `replace(f"apps/{app}/", "")` treatment before splitting. Fix: apply `node["file"].replace(f"apps/{app}/", "", 1).split("/")` in the module grouping loop.

- **[severity: low]** Security — `health_graph.py` line 28: `_exec(bench, f"cd apps/{app} && codegraph init ...")` — `app` is sanitized by `_safe()` on line 17, so shell injection is not possible here. However, the sqlite3 queries on lines 31–55 embed the sanitized `app` value directly into a shell-quoted SQL string. `_safe()` allows dots, which are valid in SQLite but the path is used as a file argument (`sqlite3 apps/{app}/...`), not in SQL — so SQL injection is not a concern. This is safe as-is, but worth noting: if `_safe()`'s allowed charset ever widens, this could become a risk.

## Verdict
NEEDS CHANGES — the force simulation leak (high) and the D3 in-place mutation of cached edge data (medium) are both bugs that will manifest in normal use. The import-edge ordering bug causes silently incomplete graphs. Fix these three before shipping.
