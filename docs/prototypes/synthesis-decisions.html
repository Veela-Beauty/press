Where does cert generation happen for the "Open in VS Code" flow?
Theirs has a one-click `generate_ssh_certificate` API + browser-download blob. Ours uses the existing SSH dialog with multi-step UX.
Option A — Use existing SSH dialog
User clicks "Open in VS Code" tile
→ VSCodeLaunchDialog opens
→ shows the existing SSH cert flow:
  Step 1: PowerShell encoding
  Step 2: echo cert > ~/.ssh/...
  Step 3: Launch VS Code button
→ User clicks Launch
Option B — One-click generate + browser download
User clicks "Open in VS Code" tile
→ VSCodeLaunchDialog opens
→ if has_valid_cert:
  Show Launch button only
→ if no cert:
  [Generate Certificate] button
  Auto-downloads `id_ed25519-cert.pub`
  Show Launch VS Code
→ User clicks Launch
Option C — Hybrid (best UX)
User clicks "Open in VS Code" tile
→ VSCodeLaunchDialog opens
→ if has_valid_cert: Launch only
→ if no cert + 1 key:
  [Generate & Download] one click
→ if no cert + multi-key:
  Open existing SSHCertificateDialog
  (key picker)
→ User clicks Launch
AExisting dialog only

  • Reuses tested dialog

BOne-click generate

CHybrid (smart default)

How should `has_valid_cert` handle multi-key users?
Their `get_ssh_certificate` only checks the user's `is_default=1` SSH key. Users who minted a cert for a non-default key (via the multi-key picker in `SSHCertificateDialog`) will see "no cert" even though one exists.
Today (theirs) — bug for power users
User has 2 SSH keys:
  - key-A (is_default=0)
  - key-B (is_default=1)
User minted cert for key-A.

get_ssh_certificate looks up key-B only
→ returns has_valid_cert=false
→ UI says "Generate Certificate"
→ user already has a valid one!
Fix — check any registered key
User has 2 SSH keys:
  - key-A (is_default=0) ← cert
  - key-B (is_default=1)

get_ssh_certificate iterates all enabled keys
→ finds cert for key-A
→ returns has_valid_cert=true
→ UI shows Launch button
ADocument the limitation, ship today
Note in wiki that multi-key users should set their preferred key as default.
  • Faster to ship
  • Affects only multi-key power users
  • Power users hit the bug
  • Tech debt
BFix it now — check any registered key
Iterate `User SSH Key` records (filter `is_disabled=0`), return first valid cert.
  • Correct for all users
  • ~10 lines of Python change
  • Slightly more backend work
